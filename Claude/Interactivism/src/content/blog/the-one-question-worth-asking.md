Before a sprint starts, before a wireframe gets drawn, there is one question that decides everything: *what does this need to do for the person using it?*

Not what the business wants. Not what the roadmap says. What does the person on the other side of the screen need to accomplish — and what's currently stopping them?

Teams that answer that question precisely build the right things. Teams that skip it build things precisely.

## Why this is hard

The question sounds obvious until you try to answer it with specificity. "Users need to onboard faster" is not an answer. "New users abandon the account setup flow at the document upload step because the interface doesn't tell them which document to use" is an answer.

The specificity is the point. A vague problem statement produces a vague solution. A precise one produces a precise intervention.

## One practice that helps

At the start of any project, write a single sentence that completes this template:

> [User type] can't [do X] because [specific obstacle].

If you can't fill it in with real evidence — from research, from support tickets, from watching someone use the product — you're not ready to build yet.
