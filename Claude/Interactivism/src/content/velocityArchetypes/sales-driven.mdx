strengthCopy: "You are close enough to revenue to know which problems are actually worth money, which is a vantage point most product teams never get. When you build something, somebody has already said they will pay for it."
failureModeCopy: "The problem is that one customer’s requirement becomes a permanent part of the product. Over a few years that accumulates into a product with several personalities: screens that work differently from one another, features exactly one account uses, and no coherent answer to what the thing is. New customers feel it as inconsistency. Your own team feels it as a codebase where every change has unexpected blast radius."
moves:
  - title: "Ask “who else?” before every one-off"
    body: "Before you commit, name three other accounts that would use it. If you cannot, build it as configuration rather than a feature, or price it as services."
  - title: "Audit single-customer features once a year"
    body: "List every feature used by exactly one customer. Some are worth keeping. Knowing which is which is worth the afternoon."
  - title: "Write the pattern down the second time"
    body: "The first time you build something it is a feature. The second time it is a pattern. Document it then, while both examples are still in front of you."
